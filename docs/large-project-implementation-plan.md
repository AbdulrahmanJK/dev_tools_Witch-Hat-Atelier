# Grimoire: план для больших проектов

Составлен по коду Grimoire и примеру `wp-calypso-trunk` с 17 044 найденными исходниками. Ниже сохранены исходные этапы и критерии готовности; актуальное состояние реализации перечислено в [дорожной карте](project-roadmap.md). Полный повторный скан Calypso и его сборка при реализации не запускались.

## Что уже исправлено на карте

Режим, который на далёком масштабе заменял все компоненты одними островами, убран. На любом масштабе карта рисует **отдельную отметку каждого видимого компонента или модуля**. Когда экран вмещает тысячи узлов, отметка упрощается до цветной точки с минимальным размером в пикселях; при приближении появляется прежняя подробная печать. Пульсация runtime остаётся видна поверх точек. Связи на самом дальнем масштабе показываются для выбранного или наведённого узла, чтобы линии не закрывали сами компоненты. Кнопка «Вместить карту» и возможность отдалить её до границ большого проекта остаются.

Это сохраняет присутствие компонентов, но у экрана есть физический предел: 17 тысяч отметок могут накладываться друг на друга. Следующие шаги должны повышать читаемость и скорость **без замены компонентов архипелагами**.

## Обнаруженные ограничения

| Область | Сейчас на большом проекте | Что требуется |
| --- | --- | --- |
| Статический разбор | Ошибки Babel на отдельных TypeScript/JSX-файлах оставляют их без точных компонентов и импортов; в журнале они выглядят как ошибки скана. | Устойчивый разбор и процент покрытия с перечнем пропусков. |
| Обновление карты | После 5000 файлов слежение за изменениями выключено; нужен ручной перескан. | Инкрементальный индекс и ограниченное слежение с понятным состоянием «карта устарела». |
| Карта и взаимодействие | Полная раскладка большого графа дорогая; поиск узла при наведении проходит по всем узлам. | Кэш раскладки, пространственный индекс, отсечение вне экрана, бюджет на линии и кадр. |
| Передача графа | Сервер отдаёт один большой JSON, браузер загружает его целиком. | Версионированная передача по частям или сжатие, с ранним доступом к карте и поиску. |
| Runtime | Автоустановка `dev:grimoire` сейчас рассчитана на стандартный Vite entry. Calypso использует Webpack и несколько приложений. | Выбор конкретного приложения/entry, адаптер Webpack и проверяемое изменение файлов. |
| Вес библиотек | Кнопка измеряет Vite-сборку; для Webpack-проекта результат недоступен. | Импорт существующего Webpack stats и ручное измерение конкретной сборки. |
| Сопоставление событий | Имя компонента может повторяться в разных пакетах; обработка событий на большой карте проходит по массиву узлов. | Индекс по файлу и стабильному ID, явная оценка точности, пакетное обновление только затронутых узлов. |

Эти ограничения относятся к анализу конкретного большого репозитория. Go, Java, Kotlin и C# продолжают получать статическую карту; runtime и измерение бандла для них не входят в этот этап.

## Принципы интерфейса

1. **Каждый компонент присутствует на основной карте.** Масштаб меняет детализацию знака и подписей, но не заменяет узлы агрегатами. При скоплении точек выбор показывает ближайших кандидатов с именами и файлами; выбранный узел подсвечивается сквозь соседей.
2. **Число всегда имеет источник.** «Оценка по исходникам», «Webpack stats» и «runtime» различаются подписью и способом расчёта. Нельзя назвать DOM-мутацию ререндером или сумму размеров общих чанков весом одной библиотеки.
3. **Дорогие операции запускает пользователь.** Скан по команде запуска ожидаем; dev-сервер и build целевого проекта Grimoire сам не стартует. Для сборки нужна отдельная кнопка с именем выбранного приложения и ожидаемым действием.
4. **Недоступная функция объясняет причину.** Вместо кнопки «Measure Vite build» в Webpack-проекте показывать «Нужны Webpack stats» и путь к действию. Состояния «обнаружено», «поддерживается», «подключено», «измерено» различать.
5. **Нагрузка ограничена.** Никакой непрерывной анимации 17 тысяч узлов; новый runtime-сигнал будит только нужный кадр. Тяжёлые этапы имеют прогресс, возможность остановки и диагностический журнал.

## Этап 0. Зафиксировать базу и возможности проекта

**Задача.** Сначала сделать состояние большого проекта проверяемым. Манифест возможностей определяет пакетный менеджер, workspaces, приложения, bundler каждого приложения, React/Vue и доступные способы подключения. Для Calypso корневой `package.json` указывает React 19 и Webpack 5; корень нельзя автоматически считать одной Vite-точкой входа.

**Реализация.** В CLI добавить описание обнаруженных приложений и сборщиков в метаданные графа. Хранить число найденных, разобранных и пропущенных файлов, длительности фаз и причину отключения watcher. В интерфейсе рядом со статусом скана показывать «17 044 файлов · N разобрано · M с предупреждениями», а в DevTools — доступные режимы выбранного приложения. Не выводить точность из одного наличия зависимости в корне monorepo.

**Готово, когда:** пользователь без терминала видит, что именно открылось, какой анализ доступен и почему кнопка runtime или сборки сейчас недоступна.

## Этап 1. Устойчивый и инкрементальный статический анализ

1. Разделить ошибки синтаксического разбора на «невозможно прочитать файл», «частично распознан» и «распознан». После сбоя строгого Babel-разбора повторять подходящей грамматикой или безопасным частичным извлечением импортов, объявлений и строк; не придумывать связи, которые не удалось подтвердить.
2. Индексировать результат по нормализованному относительному пути и отпечатку содержимого. Повторный скан меняет только затронутые файлы и зависимые связи; удаление и переименование удаляют старые узлы. Кэш должен иметь версию формата и ограничение размера на диске.
3. Для проектов свыше 5000 файлов добавить слежение за выбранным workspace или периодическую проверку изменённых файлов с ограничением частоты. Пока индекс обновляется, старая карта доступна с меткой «обновляется»; при ошибке остаётся прежний снимок.
4. Стадии `discover → parse → nodes → edges → diagnostics → dependencies → layout` получают текущий файл, число обработанных, предупреждения и замер времени. Кнопка остановки прекращает worker без бесконечного ожидания.

**Готово, когда:** один изменённый файл не требует полного разбора 17 тысяч файлов; ошибки в нескольких `.ts` не обнуляют покрытие всего проекта; пользователь видит число реально разобранных файлов и может остановить операцию.

## Этап 2. Большая карта без потери компонентов

Первый шаг этого этапа уже внесён: островной обзор заменён индивидуальными отметками узлов на дальнем масштабе. Далее:

1. Построить пространственный индекс позиций узлов и библиотек после раскладки. Наведение, клик и выбор кандидата ищут только соседние отметки, а не проходят по всему графу.
2. Разделить статический слой карты и динамические пульсации. Перерисовывать фон и тысячи неподвижных узлов только при движении камеры, изменении фильтра или графа; событие ререндера обновляет поверх него небольшой динамический слой. Сохранять визуальные эффекты на близком масштабе.
3. Сохранять индивидуальные отметки на каждом масштабе. Для плотных мест применять минимальный экранный радиус и разбор кандидатов при клике; подписи и внутренний рисунок печати показывать по мере приближения. Проверить, что точки не превращаются в нечитаемое непрозрачное пятно.
4. Ограничить рисование связей видимой областью и контекстом выбора; подготовить индекс смежности, чтобы на дальнем масштабе не обходить все рёбра на каждый кадр. Подсветка выбранного узла и его прямых связей имеет приоритет.
5. Кэшировать раскладку по отпечатку графа. Показывать карту из последнего корректного снимка, пока новая раскладка считается. Если потребуется перенос раскладки в worker, передавать компактные массивы координат, а не копии полных объектов AST.

**Готово, когда:** в режиме «Вместить карту» отмечен каждый узел, выбранный компонент можно найти и открыть, а движение/наведение не вызывает длительных подвисаний на проекте масштаба Calypso. Целевой бюджет кадра и CPU фиксируется измерением на одном MacBook Air до оптимизации и проверяется после неё; пока чисел нет, не объявлять произвольный FPS достигнутым.

## Этап 3. Подключение Webpack и monorepo runtime

1. Пользователь выбирает приложение/workspace и его dev entry. Grimoire показывает обнаруженный React/Vue, bundler, файлы, которые собирается изменить, и diff будущего адаптера. Если entry неоднозначен, предлагаются кандидаты, а не правится первый найденный файл.
2. Для React 17–19 подключать dev-адаптер до монтирования приложения. В событиях хранить страницу, ID экземпляра, родителя, файл/модуль при наличии, commit и источник измерения. React Fiber hook считать внутренним интерфейсом: при его отсутствии честно переходить к ограниченному режиму Profiler/браузера.
3. Для Vue 3 предусмотреть аналогичное подключение по dev entry и lifecycle/dev-хукам. Отдельно подписывать, доступны ли ключи реактивности.
4. Установка добавляет отдельную команду `dev:grimoire` в выбранный пакет, сохраняет исходные файлы для удаления/обновления и не перезаписывает пользовательские изменения вслепую. Удаление показывает diff и трогает только сгенерированные фрагменты. Настраивать явный локальный origin приложения без wildcard-доступа.
5. Сопоставлять runtime с печатью прежде всего по файлу/модулю и экспорту, затем по имени и дереву. UI показывает «точно», «вероятно» или «несколько кандидатов»; при неоднозначности пользователь выбирает вручную. События буферизуются и адресно обновляют узлы по ID; показывать задержку доставки и потери.

**Готово, когда:** выбранное Webpack-приложение можно подключить одной кнопкой, запустить его командой `dev:grimoire`, увидеть обновления компонентов на основной карте и безопасно удалить адаптер. Без выбранного приложения установка не выполняется.

## Этап 4. Библиотеки и Webpack stats

1. До измерения оставить оценки по импортам: сколько файлов использует библиотеку и где она находится на карте. Прямо писать «оценка по исходникам», не показывать её как вес итогового JS.
2. Сначала разрешить **импорт уже существующего** `stats.json` для выбранной сборки. Разобрать assets, chunks и modules; отделить стартовые чанки от загружаемых позже и исключать двойной учёт общих чанков. Показывать размер JS и метод расчёта, при наличии — gzip/brotli как отдельные числа.
3. Кнопку «Измерить Webpack-сборку» добавлять только при известной безопасной команде и явном нажатии. Перед запуском показать команду, рабочую директорию, ожидаемый выходной каталог и способ остановки. Не запускать весь Calypso по догадке из корневого скрипта.
4. На основной карте печать библиотеки показывает оценку/измерение, число импортёров, начальную или отложенную загрузку. В панели доступно сравнение двух снимков одной конфигурации сборки; разницу разных target/browser считать несопоставимой.

**Готово, когда:** Webpack-проект получает понятное представление библиотек без сборки, а после импорта stats — измеренные размеры с указанием источника и чанков. Vite-кнопка не предлагается для Webpack.

## Этап 5. Проверка и выпуск

Проверить три размера графа: небольшой учебный проект, `upline_admin-module` и Calypso-масштаб. Для большого проекта отдельно измерить время фаз скана, пик памяти worker, время построения карты, задержку клика/поиска, кадр при панорамировании, задержку runtime-события и нагрузку в неактивной вкладке. Сравнивать один и тот же сценарий на одной машине до и после изменений. Проверить клик по плотным точкам, «Вместить карту», переход к файлу в редакторе, отмену скана, повторный запуск и ошибочный файл. Отдельно пройти поддерживаемые React 17/18/19 и Vue 3 на малых проектах, затем одно выбранное Webpack-приложение.

Результат этапа — обновлённое пользовательское руководство: **что видно без подключения, как выбрать приложение, что делает команда, что запускается только по кнопке, чему можно доверять в цифрах**. Для каждой недоступной возможности интерфейс должен объяснять следующий шаг.

## Порядок реализации

Этапы 0 → 1 → 2 дают надёжную карту для любого языка и большого репозитория. Этап 3 зависит от явного выбора приложения/entry; этап 4 может начаться параллельно с ним через импорт существующих Webpack stats. Этап 5 сопровождает каждый этап измерениями и завершает выпуск. Ближайшая конкретная задача после уже внесённого исправления карты — манифест возможностей проекта и покрытие статического разбора: они покажут, какие из 17 тысяч файлов действительно представлены на карте.
